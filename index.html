Task Manager API

en línea

API REST de gestión de tareas: crear, listar, detallar y eliminar, con arquitectura por capas, validación con Pydantic y documentación Swagger/OpenAPI.

  • FastAPI
  • SQLAlchemy
  • SQLite
  • Pydantic
  • Uvicorn
Estudio de caso

el reto

Tomar un CRUD de tareas —aparentemente trivial— y disponerlo como API REST organizada: rutas independientes, validación estricta y una capa de persistencia desacoplada con SQLAlchemy.

arquitectura

  • Separación en capas dentro de app/: rutas, esquemas Pydantic, operaciones de BD (crud) y sesión SQLite con SQLAlchemy.
  • La sesión se inyecta por request (get_db) y se abre y cierra por petición.
  • Listado paginable con los query params skip y limit.

decisiones

  • Cada capa con una sola responsabilidad: poder reemplazar SQLite por PostgreSQL sin tocar las rutas.
  • Escribir la validación con el framework (Pydantic) antes que la validación manual en cada endpoint.
  • Esquemas de respuesta explícitos para que Swagger documente el contrato real.

endpoints

  • POST /tasks/
  • GET /tasks/?skip=0&limit=100
  • GET /tasks/{id}
  • DELETE /tasks/{id}

qué cambiaría

El modelo ya tiene el campo completed pero no hay endpoint para usarlo: añadiría PUT/PATCH /tasks/{id}. También pruebas con pytest, migraciones con Alembic y el cambio a PostgreSQL para producción.

API de Autenticación con JWT

en línea

Autenticación con registro y login, contraseñas hasheadas con bcrypt, tokens JWT con expiración configurable, roles de acceso (user/admin) y despliegue con Docker Compose.

  • FastAPI
  • PostgreSQL
  • JWT
  • bcrypt
  • Docker
Estudio de caso

el reto

Verificar quién hace cada petición, mantener la sesión sin guardar estado en el servidor y permitir que solo administradores accedan a rutas sensibles.

arquitectura

  • Las contraseñas nunca se guardan en texto plano: hash con bcrypt.
  • Sesión stateless con JWT: token firmado con SECRET_KEY y vencimiento configurable.
  • OAuth2PasswordBearer integrado con Swagger: los endpoints protegidos se prueban desde /docs.
  • Migraciones con Alembic y despliegue reproducible con PostgreSQL + Docker Compose.
  • Control de roles user/admin resuelto como dependencia de la ruta protegida.

decisiones

  • bcrypt con salt automático para el hash; nunca la contraseña cruda.
  • Configuración sensible en .env vía pydantic-settings; nada hardcodeado.
  • El token lleva el claim exp calculado en UTC y el usuario viaja en sub.
  • Suites de pruebas con pytest y migraciones versionadas.

endpoints

  • POST /auth/register
  • POST /auth/login
  • GET /users/me
  • GET /admin/users

qué cambiaría

Añadiría refresh tokens y revocación ante tokens robados, rate limit en /auth/login contra fuerza bruta y los tests corriendo en CI. También revisaría la versión de bcrypt para eliminar el warning de compatibilidad con passlib.

URL Shortener API

en línea

Acorta URLs a códigos alfanuméricos seguros generados con secrets, redirección 301, estadísticas de visitas y protección con API key y rate limiting.

  • FastAPI
  • SQLAlchemy
  • SQLite
  • Pydantic
Estudio de caso

el reto

Convertir URLs largas en códigos cortos imposibles de adivinar, redirigir al destino y medir cuántas veces se usa cada enlace.

arquitectura

  • Códigos generados con la biblioteca secrets (criptográficamente seguros) y longitud configurable; recolisión si el código ya existe.
  • Redirección 301 que además incrementa las visitas del enlace.
  • Middleware propio: valida la API key (header X-API-Key) y aplica rate limit por IP con respuesta 429 al exceder.
  • La documentación (/docs, /openapi.json) queda exenta del middleware para no bloquearla.

decisiones

  • 301 (permanente) para una redirección amigable con buscadores.
  • Proteger /shorten con API key y tope de peticiones por IP para evitar abuso.
  • Configuración central (BASE_URL, API_KEY, RATE_LIMIT, SHORT_CODE_LENGTH) en settings vía .env.

endpoints

  • POST /shorten
  • GET /r/{code}
  • GET /stats/{code}

qué cambiaría

El rate limit vive en memoria y no escala a varios workers: usaría Redis. Validaría también contra open redirect (que el destino no apunte a sitios maliciosos), añadiría pruebas con pytest y expiración de enlaces.
